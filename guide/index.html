From demo to real

How to get from this demo to the real thing

The demo runs on four small things: a register of systems and owners, a contract per data flow, one event each system sends when a message passes, and expectations for when it should arrive. Here is what each one is, how to start simple, and what we need to decide.

01ModelSystems, contracts, checkpoints. Start with a spreadsheet. 02SignalOne small event per checkpoint. No data values. 03ManageContracts as files in git, owned and reviewed. 04ExpectDeclared first, learned later, owner decides.
01 · Why

Without contracts, problems are found by the people who use the data

Most integrations work. The trouble is what happens when one doesn't: nobody is told, nobody is sure who owns it, and nobody knows what else it breaks.

Without a contract
With a contract and checkpoints
A field disappears upstreamReports quietly go wrong. Someone notices at month-end.
 The change is checked against registered readers before it ships. Breaking changes need a new major version.
A feed stops at 03:00Found at 09:00, in a meeting, by the person who needed the numbers.
 The checkpoint turns yellow minutes after it was due. The steward is told before anyone opens a report.
"Who owns this?"The ticket moves between three teams.
 Every system and every contract has a named business owner and steward.
Personal data ends up in analyticsFound in an audit.
 Data above a system's clearance is held back at the door, and the sender is named.
"What does this outage break?"Guessed.
 Read down one column: 18 contracts, 11 systems after it.

A data contract is a promise from the team that produces the data: this is what it looks like, how secret it is, when it arrives, and who to call. The checkpoints show whether the promise is being kept.

02 · Model

The data model, from simple to hard

Four levels. Each one is useful on its own, and each one builds on the previous. Most of the value arrives at level 3; level 4 is where it gets precise.

Answers who to call on its own, before any event exists. Stages are a fixed list (source, integration, Dynamics 365, apps, analytics), so the board never grows sideways. The security levels should be the ones we already use.

The route through the systems does not have to be written down: the events will show it. Listing readers is what makes impact analysis possible later.

run_id ties one message's checkpoints together; source links them into a path. The owner is not in the event, it comes from the register. records and profile describe the data without containing any of it.

Field-level readers are what let us say "removing po_number breaks the cost forecast and the procurement app" before anyone ships it. Start with the contracts that hurt most when they break.

03 · Signal

What systems should send

One small event when a message passes, and one when it fails. Never the data itself.

FieldRequiredWhy
system_id, flowYesWhich checkpoint of which contract. Owner and clearance are looked up from these.
run_idYesTies one message together across systems. Created at the source, passed along. If a system can't pass it, the batch or file name works.
sourceYesWhere it came from. The path is built from this, so nobody has to maintain it.
status, dateYesok or failed, with an ISO time and offset. The platform works out late, waiting and blocked itself.
security_levelYesHow secret the data is as it leaves. Lets the next system refuse what it is not cleared for.
records, profile, messageNoCounts and one line of text. Turns "it failed" into "112 rows had no purchase order".

Who sends it

Start hereThe integration platform, on behalf of others

Most flows already pass through the hub. One step in each integration emits the checkpoint before and after it hands data on. In the demo the hub alone covers 18 of 30 contracts.

Logic App / Function step, or an API gateway policy
BestThe system itself

The system posts the event when it finishes a run. Most precise, but needs a change in every system, so do it where it is cheap or the flow is critical.

HTTP endpoint or event stream
FallbackThe platform watches

For systems that cannot send anything: notice the file arriving, the table changing, or the Dynamics 365 business event, and write the checkpoint for them.

File drop, database watermark, D365 business events
Honest greyNobody can tell

Mark the checkpoint as not observed. A grey box that says "we don't know" is better than a green one that guesses.

Shown as unobserved, never as passing
Rule of thumb: if a system can write a log line, it can send a checkpoint. The event is small enough to send from anywhere, and it carries counts, never values.
04 · Manage

How contracts are managed

Contracts live as files in git, one per contract. Changing one is a pull request. The catalogue and the board are built from the files.

ProposeSteward edits the file and opens a pull request.
CheckAutomated: file is valid, owners exist, levels are known.
ImpactBreaking changes list the readers who use the field and notify them.
ApproveBusiness owner approves. Breaking changes also need the readers.
PublishMerged file goes live in the catalogue and on the board.

Who does what

RoleAnswers forTypical person
Business ownerWhat the data means, who may use it, approving changes.Head of the function that produces the data
StewardThe feed working, the contract file being right, announcing changes. Gets the alerts.System or integration specialist
ReaderRegistering which fields it uses. Saying yes or no to breaking changes.Owner of the report, app or model
Platform teamThe event endpoint, the register, the board, retention.Data platform

Versioning follows the usual rule: major for anything that breaks a reader (remove, rename, change type), minor for anything safe (add an optional field, a new value). The old major stays published until its last reader has moved, with a sunset date.

05 · Expect

When should a checkpoint turn yellow?

The colours are only as good as the expectations behind them. There are three ways to set them.

Declared

The owner writes the expected times into the contract: runs every 60 min, each hop within 5 min.

  • Simple, explicit, easy to explain
  • Works from day one
  • Guesses are often wrong
  • Goes stale as volumes change

Learned

The platform keeps per-checkpoint timing history and flags anything outside the normal range.

  • Fits how things really run
  • Spots slow drift nobody declared
  • Needs weeks of history
  • "Normal" can be normally bad

Both: declared limits, learned normal

Start with declared values. After enough runs, the platform learns the normal range and suggests changes; the owner accepts or rejects.

  • Works day one, gets sharper
  • The owner stays in charge
  • Declared value caps the learned one
  • A little more to build

How the recommended option decides

GreenArrived within the normal range for this checkpoint and time slot.
YellowLater than expected: the declared SLA, or the learned 95th percentile once the owner has accepted it. Worth a look, no alert.
RedPast 3× the expected time, an error, or data above the clearance. The steward is alerted.
  • Learn per time slot, not one average: weekday mornings, nights, month-end close and the Finnish holiday calendar each behave differently.
  • Wait for about 20 runs before trusting a learned value. Until then, the declared value is used on its own.
  • Never learn from bad days. Runs that failed or were red are left out, so an outage does not become the new normal.
  • Suggestions go to the owner, with the evidence: "p95 has been 3.9 min for 6 weeks; suggest 4 min instead of 5."
06 · Keep

What we keep, and for how long

Checkpoints are small but many: 30 contracts at five hops each already produce thousands a day. Keep detail short, keep summaries long. The values below are starting points to agree on.

WhatKeepWhy
Raw checkpoint events30–90 daysInvestigating a specific run. Older detail is rarely looked at.
One summary row per run13 months"When did this start?" and year-on-year comparison, such as last month-end.
Hourly counts and percentiles per checkpoint25 monthsWhat the learned expectations are built from; covers two of every season.
Learned baselines and accepted SLA changesCurrent + change historyExplaining why a box turned yellow on a given day.
Security blocksAs our audit policy saysEvidence that secret data was held back.
Data valuesNeverThe platform does not receive them in the first place.
07 · Getting there

A path that starts small

Each step is useful on its own, and each one can stop if it doesn't pay off.

  1. Sandbox NowThis demo, invented data. Agree on the model and the event.
  2. RegisterList the real systems, owners and stewards. Level 1 only; a spreadsheet is enough.
  3. Pilot three contractsPick three that hurt when they break, for example supplier invoices, worker check-ins and project budgets. The integration platform sends their checkpoints. Expectations declared.
  4. Everything through the hubEvery integration step emits checkpoints. Contracts move to git; readers register their fields.
  5. Learn and tightenLearned expectations switched on; owners review suggestions; the systems that matter most send their own events.
08 · Decide

Decisions needed from architecture

  • Where the register livesOur own small service, or a catalogue we already have (for example Microsoft Purview), with the board on top.
  • Event transportAn HTTP endpoint, an event stream, or both. Integration steps and systems need one stable address.
  • run_id standardWho creates it, its format, and how it is passed on through files, APIs and batches.
  • Security levelsMap the four levels used here to our existing classification, and decide where pseudonymisation happens.
  • Who owns the platformThe team that runs the endpoint, the board and retention, and answers when the board itself is wrong.
  • Retention and calendarsAgree the periods above, and which calendars (business days, month-end, holidays) expectations should know about.
